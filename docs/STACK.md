# Stack

This document records the mandatory stack from `docs/SPEC.md` plus the architect's
decisions on the open questions raised in `docs/QUESTIONS.json`. It is the single source
of truth for tooling/version choices; see `docs/ARCHITECTURE.md` for module design.

## 1. Mandatory stack (from SPEC.md, non-negotiable)
- Language: TypeScript 7.0.2 (frontend and backend)
- Runtime: Node.js 26.x
- Package manager: pnpm (pnpm workspaces)
- Monorepo tooling: Nx (project graph, cached tasks, `nx affected` in CI)
- Frontend: React 19.x
- Bundler: Vite (every frontend app and library)
- Microfrontends: Vite Module Federation (`@module-federation/vite`), shell host + one
  remote per domain
- Routing: TanStack Router (type-safe, file-based routes)
- Server state: TanStack Query
- UI Library: shadcn/ui on Base UI primitives, styled with Tailwind CSS
- Typography: shadcn Typeset
- Design system: `packages/ui`, documented in Storybook
- Static analysis: ESLint (flat config, typescript-eslint) + `tsc --noEmit`, as Nx targets
- Backend framework: Express
- Database: Postgres
- ORM: Prisma
- Test tools: Playwright (E2E), Vitest (unit/integration), Axe (a11y), Pact (contract
  tests), K6 (load tests)
- Containerization: Docker + Docker Compose (single `docker compose up` for the whole
  system, including Ollama)
- Observability: Prometheus + Grafana

## 2. Decisions log

| # | Question | Decision |
|---|----------|----------|
| 1 | How should auth-service issue and validate sessions? | **Stateless JWT** access token in an `httpOnly`, `Secure`, `SameSite=Lax` cookie, short-lived (15 min), paired with a longer-lived refresh token cookie. `conversation-service` validates access tokens locally via a shared JWT secret (HS256) exposed by `auth-service` through a `/.well-known/jwks.json`-style config/env, avoiding a network round trip per request. No server-side session table for access tokens. |
| 2 | Access/refresh token expiry policy | Access token: **15 minutes**. Refresh token: **7 days**. Refresh tokens are single-use and **rotate on every use** (old refresh token is invalidated in Postgres when a new one is issued), enabling revocation and replay detection. |
| 3 | Where are uploaded chat attachments stored? | **Local filesystem volume** mounted into `conversation-service` at `./data/uploads` (Docker volume in compose). Postgres stores attachment metadata (id, chat/message id, owner, original filename, stored path, mime type, size, extracted-text status). No S3/object storage in this scope. |
| 4 | Password policy for registration | Minimum **8 characters**, at least **one letter and one number**. Enforced with a shared Zod schema in `packages/shared-types`, used by both the `mfe-auth` form and `auth-service`. |
| 5 | CI platform | **GitHub Actions**, using `nx affected` for lint/typecheck/test/build on PRs, keyed on the Nx cache. |
| 6 | Test coverage target | **80% line coverage** on `services/*` and `packages/ui` business logic (hooks/model code, not stories), enforced via **Vitest coverage thresholds** (`coverage.thresholds.lines/statements/functions/branches`) and checked in CI; a failed threshold fails the build. |
| 7 | Default Ollama model for docker-compose | **`llama3.2:1b`** — pre-pulled by an `ollama-pull` init step in `compose.yaml` so local dev and E2E/CI runs start with a small, fast model available offline. |
| 8 | Correlation ID header | **`X-Correlation-Id`**. Generated by the shell app (or any API client) if not already present on outgoing requests; propagated unchanged by `auth-service` and `conversation-service` into their structured logs and echoed back on the response. A shared helper lives in `packages/shared-types` (or a small `shared/http` module) so both services and the shell implement it identically. |

## 4. Local environment
- All configuration via environment variables; `.env.example` at repo root documents
  every variable (Postgres URL, JWT secret, token TTLs, upload dir, Ollama base URL,
  default model, Prometheus/Grafana ports, correlation header name).
- `docker compose up` starts: `postgres`, `auth-service`, `conversation-service`,
  `ollama` (with a one-shot `ollama-pull` job for `llama3.2:1b`), `prometheus`,
  `grafana`, and the frontend `shell` (serving the built shell + remotes, or `vite
  preview`/dev servers for local dev).
- OpenAI and Anthropic are called directly from `conversation-service` using the
  per-request key sent by the browser (FR19); no local mock service is required, but
  provider adapters must be mockable in tests.
