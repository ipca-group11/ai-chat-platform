Appendix

Claude, Workflows & Skills

How Claude Code was actually used to produce the testing work in this report, and how to run the same process again. Written for transparency, not as a sales pitch for the tool.

What Claude Code is

Claude Code is a command-line AI assistant that can read and edit files, run shell commands, browse the running app, and talk to external services like Jira over a controlled connection called MCP (Model Context Protocol). In this project it was used as a pair-programmer for the testing work, not as a replacement for deciding what to test.

Every decision about what matters, which 5 functionalities to cover in Part 1, which risks justify a Critical priority in the NFR page, was made by the team. Claude Code carried out the resulting work: writing epics and stories in Jira, writing this report, running real commands and capturing their real output.

What it actually did on this project

Jira content

Wrote and rewrote the 30 testing epics and their stories directly in Jira, through an Atlassian connection, in the same tone and structure as the rest of the board.

This report

Built every page in docs/report/, pulling the Jira content, the architecture docs and the real test commands into one site.

Running real tests

Executed the project's actual Vitest, Playwright and scanning commands against the running stack, and kept the real pass/fail output, including real failures, as evidence.

Screenshots

Drove a real Chromium browser through Chrome DevTools to capture the screens on The Project page and several evidence pages.

Workflows: running many tests at once

A workflow is a script that fans a task out across several Claude Code agents that run at the same time, each one scoped to a single test type. It was used here to collect real evidence for a large batch of the 30 test types in one pass instead of one at a time.

Each agent ran its own real command, for example pnpm exec vitest run for a unit-testing agent, or a Trivy scan for a container-scanning agent, and reported back a fixed shape: whether it ran, a short summary, and the real terminal output. Nothing was invented to fill a gap. Where a tool was missing locally or needed infrastructure that could not be touched safely, the result honestly says so instead of making up a result.

How to use this yourself

Anyone with access to this repository and Claude Code can repeat this process. There is no special setup beyond what is already in Tech Stack and Architecture.

  1. Start the app locally (see Run it locally), so there is something real to test against.
  2. Ask Claude Code, in plain English, for the specific test type or evidence you need, for example "run the unit tests for conversation-service and show me the result."
  3. For a large batch across many test types at once, ask it to use a workflow, so each type runs as its own independent agent instead of one at a time.
  4. Review the actual output before trusting it. Every evidence page in this report links back to the real command that produced it, so it can always be re-run and checked.

What this process does not replace

Claude Code did not decide what the application should do, what counts as a bug, or which risk deserves a Critical rating on the NFR page. Those calls stayed with the team. It also never ran anything destructive against the shared development stack, commands that would stop or reset the running containers were treated as off-limits throughout this work.
