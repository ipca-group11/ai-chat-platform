Part 2

Automated Tests

This page is the assignment's Part 2 deliverable: the 5 functionalities from Part 1, automated with Playwright. Each step and check follows the acceptance criteria and test cases already defined.

Is this all the automated tests? No, it's just the 5 Part 1 asks for. The project as a whole automates 28 of its 30 test types: unit, integration, contract, API schema, every security scan, performance, accessibility, load, and more, each already running in CI. The only two that aren't fully automated are penetration testing (a scripted check plus a manual, time-boxed review, by nature) and visual regression (documented in Jira, not yet wired into the Playwright config). See the full picture on Functional Tests and Non-Functional Tests, each type links to its own "How to run" page and a page of real captured evidence.

Why Playwright

The app is four micro-frontends loaded together behind one shell, with a login-gated flow and a streaming chat UI. Playwright handles all three cleanly: real browser automation, built-in waiting for streamed content to finish rendering, and network interception to mock the AI provider or simulate a failed request. It's also free, actively maintained, and already the tool used across the rest of this project's end-to-end suite.

A real excerpt: login.spec.ts

TC2 from Part 1 (wrong email/password → one generic error) and TC6 (empty field blocks the request), as they're actually implemented:

e2e/src/tests/login.spec.ts 
const invalidCredentials = [
  { name: "unknown email", email: "nobody@example.com", password: "Passw0rd1" },
  { name: "wrong password", email: "tester@example.com", password: "Wrong0pass" },
  { name: "malformed email", email: "not-an-email", password: "Passw0rd1" },
];

for (const { name, email, password } of invalidCredentials) {
  test(`Invalid credentials show one generic error: ${name}`, async ({ page }) => {
    await submitLogin(page, email, password);
    await expect(page.getByTestId("login-error")).toHaveText("Invalid email or password");
    await expect(page.getByTestId(/-error$/)).toHaveCount(1);
    await expectStillOnLoginPage(page);
  });
}

const emptyFields = [
  { email: "", password: "Passw0rd1", message: "Email is required" },
  { email: "tester@example.com", password: "", message: "Password is required" },
];

for (const { email, password, message } of emptyFields) {
  test(`An empty field blocks the sign-in`, async ({ page }) => {
    const loginRequests = trackLoginRequests(page);
    await submitLogin(page, email, password);
    await expect(page.getByTestId("login-error")).toHaveText(message);
    expect(loginRequests).toHaveLength(0); // never reaches the server
  });
}

Where this runs

  • Every pull request, against the full stack started with Docker Compose.
  • Chat specs that would need a live AI provider key run against the mock backend instead, same assertions, no cost, no flaky network.
  • A failing spec blocks the merge, same as any other CI check.
