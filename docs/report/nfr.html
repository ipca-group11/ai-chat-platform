Non-Functional Requirements

A functional requirement says what the app does. A non-functional requirement says how well it has to do it: fast enough, secure enough, available enough. This page uses ISO/IEC 25010, the standard software quality model, to name those qualities precisely and say which ones matter most for a multi-user chat app holding a person's own AI provider key.

ISO/IEC 25010, the 8 quality characteristics

Priority for this project

Security and Reliability rank highest because of what this app actually is: a multi-user service holding chat history and routing a person's own paid AI provider key. Compatibility and Portability rank lowest because the project targets one browser engine and one deployment environment by design, not because they don't matter at all.

Each characteristic, in detail

Security
Critical

Confidentiality, Integrity, Non-repudiation, Accountability, Authenticity

A leaked provider API key or another user's chat history is the worst thing this app could do. 10 of the 30 testing epics exist for this alone: SAST, DAST, penetration testing, dependency and container scanning, SBOM, secret scanning, prompt injection, PII masking, GDPR retention.

See the security test types →
Reliability
Critical

Maturity, Availability, Fault Tolerance, Recoverability

Four micro-frontends and a streaming connection give this app more ways to partially fail than a single-page app has. Remote failure/fallback, SSE reconnection, concurrency, and stream cancellation are each their own epic specifically to catch those partial failures.

See the resilience test types →
Performance Efficiency
High

Time Behaviour, Resource Utilisation, Capacity

Measured directly: LCP/INP/CLS budgets per page via Lighthouse CI, and a k6 load test that ramps virtual users until the 4 GB production VM saturates, so the real capacity ceiling is a written-down number, not a guess.

See performance testing →
Functional Suitability
High

Functional Completeness, Functional Correctness, Functional Appropriateness

Technically a functional, not non-functional, characteristic in ISO 25010, included here because it anchors everything else: Part 1 and Part 2 of this report, plus unit, integration, contract and API schema testing, exist to prove it.

See Part 1 →
Usability
Medium

Appropriateness Recognisability, Learnability, Operability, User Error Protection, UI Aesthetics, Accessibility

Accessibility is formally tested (WCAG 2.1 AA via axe-core) and visual regression is planned for the UI-aesthetics side. The other sub-characteristics, learnability, operability, are not formally measured, a reasonable gap for a small app with one core flow.

See accessibility testing →
Maintainability
Medium

Modularity, Reusability, Analysability, Modifiability, Testability

Modularity comes from the pod/micro-frontend split itself. Testability is the one sub-characteristic with a dedicated epic: the mock server exists specifically so every other test type can run without a real database or a paid API key.

See the mock server →
Compatibility
Low

Co-existence, Interoperability

No dedicated test type. The Playwright config currently runs one browser project (Chromium); there is no cross-browser or third-party-integration surface to test against beyond the two LLM provider APIs, which are covered under Reliability and Functional Suitability instead.

Portability
Low

Adaptability, Installability, Replaceability

Addressed architecturally rather than by a test type: Docker Compose makes the whole stack installable in one command on any machine with Docker, and every config value is an environment variable. Not actively tested as a standalone quality attribute.

Quality in use

ISO 25010's second model: not the product itself, but the outcome when a real person uses it in context. Five characteristics, each with a one-line read on this project.

CharacteristicWhat it meansFor this project
EffectivenessAccuracy and completeness of reaching a goalDoes a sent message reliably produce the right stored, streamed reply? Covered by functional and resilience testing.
EfficiencyResources spent reaching that goalHow fast the reply starts streaming and how light each page loads, covered by Performance Efficiency testing.
SatisfactionUsefulness, trust, pleasure, comfortNot formally measured, no user research or satisfaction survey in this project's scope.
Freedom from riskEconomic, health & safety, environmental risk mitigationMainly economic here: a leaked key or a runaway load could cost the user money, which is exactly what Security and Load testing guard against.
Context coverageWorks across different situationsLimited: one browser engine tested, one deployment target, no offline or low-bandwidth scenario testing.
