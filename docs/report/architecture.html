Architecture

How the system is put together, as C4 diagrams, and how to run it on your own machine. Source: docs/ARCHITECTURE.md, docs/DEPLOY.md.

C4 context

One user-facing system, two external AI providers. The provider key is entered by the user and sent per request. It is never stored on the server.

C4 containers

Only shell is a single published entry point. The browser calls every other remote and service directly, their URLs are baked into the built JavaScript at image-build time.

The one exception is mfe-chat, whose API client defaults to a same-origin /api path, proxied by shell to conversation-service.

C4 component: conversation-service

conversation-service is one deployable container, but internally split into controllers, a provider adapter layer, and repositories. The adapter layer is what makes provider-adapter testing and remote-failure testing possible: both providers sit behind the same interface, so a fault can be injected at one seam instead of two.

Sequence: sending a message and streaming a reply

The provider's own key never reaches the server's database, it travels only inside this one request and is discarded once the reply finishes streaming. Every arrow after the first token chunk repeats per token, which is what sse-reconnection and stream-cancellation testing target: dropping or interrupting the connection mid-loop.

Deployment

Everything in production runs on a single Azure VM, as the same containers from the diagrams above, pulled from GHCR already built and already scanned. Caddy is the only container with a public port, every other service is reachable only inside the VM's Docker network.

Run it locally

Terminal
cp .env.example .env   # optional, every variable has a safe local default
docker compose -f compose.yaml up --build

Open http://127.0.0.1:8000/ once shell reports healthy. Register, add a provider API key in Settings, then start chatting.
