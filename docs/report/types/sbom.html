Non-Functional Tests/SBOM generation

SBOM generation

View on Jira, AICHAT-30 ↗ How to run → Evidence →
Security Non-functional White-box
What it checks

A full, versioned list of everything inside each shipped image. It's what the vulnerability scan above actually checks against.

Tooling
  • Syft / docker buildx --sbom
Cadence

Every image build, kept as a CI artifact.

Full epic details, from Jira

Description

This covers generating a software bill of materials for everything we ship - every container image at build time, plus the pnpm workspace on every pull request - so we always know exactly what's inside, and vulnerability scanning can run against that inventory instead of re-inspecting things from scratch each time.

Inputs
  • The container images we build, both first-party services and third-party base images
  • The workspace's dependency manifests and lockfile
  • Build and pull request events that trigger generation
Acceptance Criteria
  • Every image produced by a build comes with an SBOM and a provenance attestation.
  • Those SBOMs stay downloadable and checkable later against the deploy that produced them.
  • The SBOMs are scanned for known vulnerabilities, with high or critical findings blocking the pipeline.
  • The pnpm workspace gets its own comparable SBOM generated on every pull request.
Tooling / Tech Stack
  • BuildKit SBOM and provenance attestations
  • Syft and Grype
  • CycloneDX format
Definition of Ready
  • The SBOM format and storage approach are agreed before any generation work starts.
Definition of Done
  • SBOM generation and vulnerability scanning both run automatically in CI.
  • A failure in either blocks the pipeline.
  • Coverage spans first-party images, third-party base images, and the workspace itself.
