Functional Tests/Concurrency testing

Concurrency testing

View on Jira, AICHAT-13 ↗ How to run → Evidence →
Core user flows Functional Black-box
What it checks

Two sends fired at once, or a retry while a reply is still streaming. The result has to be exactly as many messages as were actually sent. No duplicates, and nothing silently lost.

Tooling
  • Vitest/integration tests with simulated network jitter
  • Playwright for the two-tab scenario
Cadence

Every pull request.

Testing strategy

The races live in services/conversation-service/src/integration, running against the real app, queue and processor with only the LLM scripted. Each scenario is checked twice: once against the in-memory repository as it answers instantly, and once with a seeded random delay of 0 to 3 ms wrapped around every repository call, standing in for a database round trip and giving two requests room to overlap between a read and a write. The seed makes a failing run repeatable.

Retry vs. streaming replya retry while another reply streams1 runRetry is queued, not dropped, and runs only after the current reply finishes
Two retries at oncethe same failed message retried twice simultaneously50 seeded runs x 2 latency modesOne 202, one 409 MESSAGE_NOT_RETRYABLE, only one call reaches the LLM
Edit vs. reply startingan edit landing 0-5 ms around a reply's start, offset = seed % 650 seeded runs x 2 latency modesEither a 200 that the model actually saw, or a 409 MESSAGE_NOT_EDITABLE, both outcomes must show up across the 50 runs
Cancel vs. reply startinga cancel landing 0-5 ms around a reply's start, offset = seed % 650 seeded runs x 2 latency modesEither a 204 and no LLM call, or a 409 MESSAGE_NOT_CANCELABLE, both outcomes must show up across the 50 runs

A run only passes if nothing in the result looks wrong: no duplicate or missing question, no message left in a status other than "sent", no reply built from a history that still included something unanswered. For the two true race scenarios (edit-vs-start, cancel-vs-start) the suite also asserts that across the 50 runs both outcomes were actually observed, a pass where every run landed the same way would mean the timing window was never hit, not that the race is safe.

Full epic details, from Jira

Description

This epic covers testing how the chat platform behaves when more than one thing happens at the same time: two messages landing in the same chat together, someone retrying or cancelling while a reply is still streaming, or several people in a shared chat typing at once. It matters because the one thing users trust a chat app to get right is their message history, a race condition that drops, duplicates, or scrambles a message is something people notice immediately, and it undermines confidence in the whole product.

Inputs
  • Multiple send, retry, edit, and cancel actions happening close together or at the exact same time
  • Several people active in the same shared chat at once
  • The queue and streaming state the chat relies on internally
Acceptance Criteria
  • Messages sent at the same time to the same chat are never duplicated and never silently dropped.
  • Retrying, editing, or cancelling a reply while it's streaming always leaves the chat in a single, consistent state, never two replies running at once, never a half-saved message.
  • When several people are active in the same chat at the same time, everyone ends up seeing the exact same messages in the exact same order.
  • The internal queue that chat messages pass through holds up correctly under many simultaneous operations, with no race conditions.
Tooling / Tech Stack
  • Vitest for queue- and service-level concurrency tests
  • Playwright for end-to-end multi-browser scenarios
  • A race-detecting test harness for repeated, randomized-timing runs
Definition of Ready
  • The expected outcome for each kind of concurrent scenario is agreed before the tests that rely on it are built.
Definition of Done
  • All the concurrency scenarios above are covered by automated tests that run in CI.
  • A failure in any of them blocks the merge.
  • Evidence from the underlying tests is available to back up this epic's results.
