Functional Tests/Snapshot testing

Snapshot testing

View on Jira, AICHAT-20 ↗ How to run → Evidence →
Quality foundation Functional White-box
What it checks

Only small, stable outputs, serialized DTOs and SSE frames, are snapshotted. Whole component trees are not, because they break on every unrelated change and stop meaning anything.

Tooling
  • Vitest snapshot serializers
  • A lint rule against oversized snapshots
Cadence

Every pull request.

Testing strategy

Every DTO fixture in packages/shared-types/src/__fixtures__/dto-snapshots.test.ts is pinned with toMatchInlineSnapshot: user profile, auth response, access token claims, chat, chat member, message, attachment, test-connection response and the error response shape, about ten in total. The six SSE event types the streaming pipeline emits (token, reasoning, web_fetch, done, error, queued) are parsed through the same schema and checked together as one file snapshot. Ids and dates never go into the snapshot as themselves: a serializer from @platform/test-config normalises them to <uuid> and <date> first, so a snapshot only breaks on a real shape change.

The wire frames get the same treatment on the server side: sse.snapshot.spec.ts snapshots the exact event:/data: text written to the response for every event type, and error-handler.snapshot.spec.ts pins the JSON body for seven HttpError status codes (400 to 500), run in both conversation-service and auth-service so the two services can't drift from each other's error shape.

RuleScopeEnforces
platform/no-component-snapshots.test.tsx / .spec.tsx filesAny snapshot matcher is a lint error; component tests must assert on roles and text instead
vitest/no-large-snapshotsevery test filemaxSize: 50 lines per inline snapshot, so a snapshot stays a data shape, not a dump

Snapshots are refreshed locally with vitest -u, never in CI, and a changed snapshot needs a reason in the pull request, per the comment at the top of the DTO test file.

Full epic details, from Jira

Description

This epic covers snapshot testing for the shared data contracts the platform depends on, the DTOs passed between the chat frontend, the conversation service, and auth, plus the raw server-sent event frames used for streaming AI responses. Rather than checking rendered pixels, this snapshots the actual data shapes, catching silent drift in a contract before it breaks something downstream that depends on it.

Inputs
  • Canonical fixture objects for the shared DTOs
  • Sample SSE frames for each event type the streaming pipeline emits
  • The type definitions these contracts are built from
  • In practice that's about ten DTO fixtures (user profile, auth response, chat, message, attachment, and so on) plus the six SSE event types (token, reasoning, web_fetch, done, error, queued), and the same error-body table, seven HttpError status codes from 400 to 500, checked against both conversation-service and auth-service.
Acceptance Criteria
  • A change to a shared DTO's serialized shape is caught by a failing snapshot before it reaches main.
  • A change to the SSE wire format used for streaming responses is caught the same way, including for error and heartbeat frames.
  • Snapshots stay small and targeted at specific data shapes rather than ballooning into full component-tree dumps.
  • The frontend's stream parser and the shared type definitions it depends on can't silently drift apart without a test catching it.
  • Concretely, the ESLint rule caps any inline snapshot at 50 lines and blocks snapshot matchers outright in .tsx test files, so a component test has to assert on roles and text instead of a markup dump.
Tooling / Tech Stack
  • Vitest snapshot testing
  • TypeScript's type system for structural comparisons
  • A custom ESLint rule to keep snapshots targeted and reasonably sized
Definition of Ready
  • The underlying DTOs and SSE frame formats are stable enough to build fixtures and snapshots against.
Definition of Done
  • All of this area's snapshot and drift checks run automatically in CI, and a failure blocks the merge until it's reviewed.
  • A changed snapshot has to carry a reason in the pull request, and snapshots are only ever refreshed locally with vitest -u, never written or accepted during the CI run itself.
