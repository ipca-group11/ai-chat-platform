Non-Functional Tests/GDPR retention and deletion testing

GDPR retention and deletion testing

View on Jira, AICHAT-33 ↗ How to run → Evidence →
Security Non-functional White-box
What it checks

Deleting a user's account actually removes their chats, messages, uploaded files and telemetry. This is checked against a real database, not assumed from the code.

Tooling
  • Vitest
  • Testcontainers Postgres
Cadence

Every pull request.

Testing strategy

Each retention job (retention/run.ts in auth-service and conversation-service) is a pure function of a clock, so the tests drive it with any now instead of waiting on real time. Every cutoff is boundary-tested at four points: one second before the limit, exactly at it, one second after, and a value that is clearly not due yet, against a real Testcontainers postgres:16-alpine and, for the file sweep, a real upload directory with file ages set through utimes.

DataRetention windowJob
Refresh tokens7 days after they expire (expired or revoked alike)auth-service retention job
Inactive accounts24 months with no sign-in or token refreshauth-service retention job, cascades to conversation-service erasure
Orphaned upload files24 hours with no attachment row pointing to themconversation-service retention job
Chats, messages, attachmentsKept until the user deletes them or the accountDELETE /auth/me, erasure endpoint

Account deletion itself is covered as one integration suite running both services for real against a single Postgres (account-deletion.db.spec.ts): auth-service calls conversation-service over an actual HTTP erasure request, so the cross-service contract is exercised, not mocked. It checks the two shared-chat cases (deleting the chat owner erases it for everyone; deleting a participant only removes their own membership, messages and files) and the partial-failure paths: conversation-service unreachable, conversation-service answering with an auth error, and the local user-row delete failing after the remote erasure already succeeded. Every one of those fails the request with 502 and leaves the account intact so the same request can simply be retried, and a retry after a full success still answers 204 instead of erroring.

Full epic details, from Jira

Description

This epic covers the platform's GDPR obligations around data retention and account deletion: making sure old data doesn't get kept longer than it should, and that deleting an account actually removes everything tied to it - chats, messages, files and telemetry - rather than leaving fragments behind. These aren't nice-to-haves; they're legal requirements, and getting them wrong has real consequences for users and for the business.

Inputs
  • Agreed retention periods for different kinds of stored data, such as chats, files and telemetry logs
  • Test databases seeded with data at different ages relative to those retention periods
  • Account deletion requests exercised against a real database and file storage layer
Acceptance Criteria
  • Retention periods for every kind of stored data are agreed, documented and enforced by a tested job.
  • Deleting an account removes all of that user's chats, messages, files and related data, verified against a real database rather than assumed.
  • Data is purged right at its retention cutoff, not noticeably early or late.
  • Misconfigured retention settings are caught automatically rather than silently reaching production.
Tooling / Tech Stack
  • Testcontainers with a real Postgres instance for database-backed verification
  • Integration test suites covering deletion and retention behaviour
  • Configuration tests for deployment-level retention settings
Definition of Ready
  • Retention periods and deletion rules are agreed before any of the underlying tests or code are built.
Definition of Done
  • Every piece of deletion and retention behaviour in this area is covered by an automated test that runs continuously.
  • A failing test blocks the merge, since this is a compliance control, not an optional check.
