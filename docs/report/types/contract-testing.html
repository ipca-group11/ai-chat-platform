Functional Tests/Consumer-driven contract testing

Consumer-driven contract testing

View on Jira, AICHAT-11 ↗ How to run →
Chat correctness Functional Black-box
What it checks

Each micro-frontend records exactly what it expects from a service call; the service replays those recordings against its real code. A breaking change is caught before either side ships, without either side needing the other running.

Tooling
  • Pact JS
Cadence

Every pull request, on both the consumer and provider side.

Full epic details, from Jira

Description

Consumer-driven contract testing makes sure every frontend app and the backend service it talks to agree on the shape of their requests and responses, so a breaking change to an API is caught automatically at the pull request stage rather than surfacing later in a broader test, or worse, in production.

Inputs
  • The frontends and services involved, and the requests they exchange
  • The agreed place where contracts are stored and shared
  • Request/response fields such as credentials, session data and chat message payloads
Acceptance Criteria
  • Every frontend-to-service call in the system has an agreed, documented contract.
  • Each frontend's expectations are captured as a contract and checked automatically.
  • Each service verifies its real behaviour against every contract published against it before it's considered safe to deploy.
  • A breaking change anywhere in this chain is caught by CI and blocks the merge, rather than being discovered later.
Tooling / Tech Stack
  • Pact JS for writing and verifying contracts
  • CI pipeline integration for the consumer and provider checks
Definition of Ready
  • The scope of this testing area is agreed, including which frontends and services are in it and where contracts are shared.
Definition of Done
  • Contract checks run automatically in CI, a failure blocks the merge, and evidence of them running lives on the individual checks.
