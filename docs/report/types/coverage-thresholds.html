Non-Functional Tests/Coverage thresholds

Coverage thresholds

View on Jira, AICHAT-34 ↗ How to run → Evidence →
Quality foundation Non-functional White-box
What it checks

A minimum line/branch coverage percentage per project. It is a floor that stops obvious gaps, not a target to chase. Passing it says nothing about whether the tests are actually any good.

Tooling
  • Vitest coverage (v8)
Cadence

Every pull request; a drop below the threshold fails CI.

Testing strategy

Every project's own Vitest config spreads a shared threshold object from packages/test-config/coverage-thresholds.ts into its test.coverage.thresholds option, using the v8 coverage provider. The floor is 80% for lines, statements and functions everywhere. Branches are 80% by default, 75% for apps/* and packages/test-utils, and 70% for e2e, since UI branching and end-to-end helper code carry more paths that are impractical to hit directly.

ScopeLinesStatementsFunctionsBranches
Default (services, packages)80%80%80%80%
apps/*, packages/test-utils80%80%80%75%
e2e80%80%80%70%

A second check, packages/workspace-config/src/coverage-guard.ts, runs as its own Vitest suite and walks every apps, services and packages directory with an Nx test target. For each one it confirms the test command actually runs with --coverage, the Vitest config imports the shared @platform/test-config preset, and the resolved threshold values are at or above the approved floor for that project's scope, failing the build if any value is missing, lowered, or not statically resolvable from the config text. Only one project, testing/k6, is exempt, because it is k6 runtime script text with no Node source to instrument, and every exemption needs a written reason or the guard's own test fails.

This runs per pull request as part of nx affected -t test in CI: each affected project's own coverage run fails the job the moment it drops below its threshold, and a separate step collects every project's coverage-summary.json into one lines/branches/functions/statements table in the job summary, so a regression is visible on the PR even for projects that still pass their floor.

Full epic details, from Jira

Description

This epic makes sure every test project in the platform actually enforces a minimum code coverage threshold, rather than having a config that looks right on paper but silently lets some projects skip the check. It covers agreeing the numbers, sharing one coverage configuration across all projects, closing the gap in the projects that weren't actually enforcing it, tightening overly broad excludes, guarding against the same gap reappearing, and showing coverage on every pull request so a drop is visible and blocks the merge.

Inputs
  • Coverage output from each test project's run
  • The agreed line/branch threshold and ratchet policy for projects below it
  • Each project's exclude patterns and test script configuration
Acceptance Criteria
  • Every test project in the platform runs with coverage enforcement, with none silently exempt.
  • A coverage drop below the agreed threshold fails the pull request's CI check.
  • Reported coverage numbers are accurate, not inflated by overly broad exclude patterns.
  • A project that's missing coverage instrumentation is caught automatically rather than discovered later.
Tooling / Tech Stack
  • Vitest coverage-v8
  • A shared coverage preset used across all test projects
  • GitHub Actions for CI enforcement and PR reporting
Definition of Ready
  • The coverage threshold and ratchet policy are agreed before enforcement work starts.
Definition of Done
  • All child stories meet their own definition of done.
  • Coverage enforcement runs automatically in CI across every test project.
