Functional Tests/SSE reconnection testing

SSE reconnection testing

View on Jira, AICHAT-9 ↗ How to run → Evidence →
Core user flows Functional Black-box
What it checks

The network drops mid-stream, on purpose. The UI has to resume or show a clear error, but it can never just hang forever.

Tooling
  • Playwright network emulation
Cadence

Every pull request.

Testing strategy

sse-reconnect.test.ts in mfe-chat drives a fake EventSource under vitest's fake timers, so the drop and the recovery happen on virtual time, not a real clock. The drop itself is a single call, source.emitTransportError(), fired while new messages keep landing server-side that the client never saw live.

ParameterValueWhere it comes from
Resync budget5,000 msRESYNC_BUDGET_MS, the test's pass bar
Browser's own EventSource retry3,000 msBROWSER_RETRY_MS, the spec default
App-level reconnect after the browser gives up3,000 msRECONNECT_DELAY_MS in stream-registry.ts

Backend keepalive heartbeat15,000 msHEARTBEAT_INTERVAL_MS in conversation-service/.../streaming/routes.ts

There is no server-side replay buffer at all: the comment in stream-registry.ts spells it out, events published while the connection is down are just lost. So the reconnect logic does not ask the backend to catch it up, it refetches the chat's full message list once the stream reopens and merges that onto what is already shown, matching by message id so a replayed event never creates a duplicate. Three cases are checked: every message persisted during the outage is present within the 5s budget with no duplicates and none missing, a message the server replays after the drop does not get added twice, and the stream itself stays subscribed through the drop (not closed) so the browser's own retry, not a fresh connection, is what brings it back.

Full epic details, from Jira

Description

This epic covers making sure the chat doesn't fall apart when the network does. The assistant's replies stream in over a live connection, and that connection can drop for all sorts of mundane reasons - a flaky wifi signal, a phone switching networks, a laptop going to sleep. This area of testing makes sure that when it happens, the app reconnects cleanly on both the frontend and backend, and the person chatting never ends up staring at a frozen screen with no idea what's going on.

Inputs
  • A live streaming reply that gets interrupted partway through
  • How long the backend is willing to hold onto a dropped stream before giving up on it
  • The retry and backoff behaviour on the frontend side
Acceptance Criteria
  • A dropped connection is retried automatically, and the user sees a clear indicator that it's happening rather than a silent freeze.
  • A reconnect that succeeds in time picks the conversation back up with no missing or duplicated text.
  • A reconnect that can't succeed in time ends in a clear, actionable error rather than an endless spinner.
  • The backend only holds onto a dropped stream's data for a bounded window before releasing it.
Tooling / Tech Stack
  • Vitest for the frontend reconnect logic
  • The conversation-service test suite for backend resume/expiry behaviour
  • Playwright for the full end-to-end network-drop scenario
Definition of Ready
  • The expected reconnect-vs-fail behaviour, retry limits and resume window are agreed and documented before any of the testing work starts.
Definition of Done
  • The frontend and backend reconnect logic are both covered by automated tests that run in CI.
  • The full end-to-end scenario passes reliably and a failure blocks the merge.
