Visual regression testing

View on Jira, AICHAT-19 ↗ How to run → Evidence →
Non-functional Non-functional Black-box
What it checks

Pixel-diffed screenshots of the key screens, in both themes. This catches a layout break that a functional assertion wouldn't notice, because the text is still technically there.

Tooling
  • Playwright's toHaveScreenshot
  • Fixed fonts and seeded data for stable renders
Cadence

Designed to run on every pull request once wired in; not yet part of CI, see the strategy section below.

Testing strategy

Designed, not yet merged

The strategy below is fully designed and documented in docs/AICHAT-19/RUNNING.md, but it has not landed on main. The current e2e/playwright.config.ts defines one project, chromium, and no visual project or baseline images exist in the repo yet. This page states the plan as a plan, not as something already running, to match what the evidence page and the automation status table already say honestly.

The plan: a dedicated visual Playwright project screenshots nine key screens (login, a login validation error, register, chat list empty, chat list with chats, chat detail with messages, the new chat dialog, settings, and the remote-failure fallback) in light and dark theme, 18 images in total. Renders would come only from the pinned Playwright Docker image (mcr.microsoft.com/playwright:v1.63.0-noble), since fonts and anti-aliasing differ enough between macOS, Windows and Linux that a locally generated baseline would not match CI. No backend would be needed: the production builds of the shell and remotes are served directly, every API call answered with fixed JSON, the clock frozen at a fixed timestamp.

Full epic details, from Jira

Description

Visual regression testing catches UI changes that functional tests don't look for, like a layout shift, a broken style, a missing icon, or a theme that stopped applying correctly. It works by comparing a screenshot of each key screen against a committed reference image on every pull request, in both light and dark theme, so a visual bug gets flagged before it reaches users.

Inputs
  • The platform's key screens, reachable in a stable, predictable state
  • A fixed rendering environment: pinned fonts, a frozen clock, and seeded test data, so screenshots don't vary for reasons unrelated to the UI
  • Light and dark theme variants of each screen
Acceptance Criteria
  • Every key screen has a committed reference screenshot for light and dark theme.
  • A pull request that changes a screen's appearance beyond an agreed threshold fails its CI check and blocks merging.
  • A reviewer can see exactly what changed, visually, without needing to run anything locally.
  • Updating a baseline on purpose, after a real UI change, is a documented, reviewed step rather than something done quietly.
Tooling / Tech Stack
  • Playwright's screenshot snapshot testing
  • Docker, to keep screenshot rendering consistent between machines and CI
  • CI artifact upload for diff images
Definition of Ready
  • The screens to cover, and what counts as an acceptable visual difference, are agreed.
  • The UI is stable enough, already covered by unit and component tests, that baselines are meaningful rather than chasing a moving target.
Definition of Done
  • The visual suite runs automatically on every pull request and blocks merge on a real diff.
  • Baselines exist for every key screen in both themes, and the process for updating them is documented.
