Non-Functional Tests/Secret scanning

Secret scanning

View on Jira, AICHAT-31 ↗ How to run → Evidence →
Security Non-functional White-box
What it checks

No API key, password or token ever gets committed to the repository. Checked on every change, and once across the project's full history.

Tooling
  • gitleaks
  • GitHub secret scanning
Cadence

Every pull request, plus a one-off full-history scan.

Testing strategy

One tool, gitleaks 8.28.0, run at three points with the same .gitleaks.toml config, which just extends gitleaks' built-in rule set ([extend] useDefault = true) and adds no rules of its own. Allow-list entries are only permitted for test fixtures, each with a comment explaining why and a narrow exact path or regex, never a broad glob; right now the list holds a single entry, for the throwaway password in an earlier version of the mock smoke-test script.

WhereCommandWhat happens on a hit
Local pre-commit hookgitleaks git --pre-commit --staged --redactCommit is blocked; if gitleaks isn't installed the hook prints a warning and lets the commit through so nobody is locked out
CI, every PR and push to maingitleaks git --redact --config .gitleaks.toml --log-opts="base..head"Job exits non-zero, merge is blocked
One-off full historygitleaks git --redact --log-opts='--all -m'Documented in a report, not wired into CI

The CI job pins the gitleaks binary by version and verifies its SHA-256 against the release's checksums file before installing it, checks out full history (fetch-depth: 0) so the base..head commit range actually exists, and writes a short pass/fail summary with the scanned range to the job summary. Every run uses --redact, so a caught value never appears in a log.

The one-off history scan (2026-10-03) covered all local and remote branches with --all -m: 45 commits in the repository, 43 of them with a textual diff to scan, 0 findings. Separately, a scan of the working tree found 7 hits in a git-ignored, never-committed local file holding real credentials for the deployed environment; those are recorded, not rotated, since the file never reached the repository.

Full epic details, from Jira

Description

This epic covers automated secret scanning for the repository: catching credentials before they're committed, before they merge, and sweeping the full project history for anything that slipped through earlier. It matters because a leaked key for one of the AI provider adapters, the database, or auth is directly usable by whoever finds it, unlike most other static-analysis findings which just point at a weakness.

Inputs
  • The repo's working tree, PR diffs, staged commits, and full git history, each scanned at a different point
  • A shared allow-list of known fixtures and test credentials
Acceptance Criteria
  • A real secret introduced anywhere - a local commit, a PR, or already sitting in history - gets caught rather than slipping through.
  • Known test fixtures don't get flagged as false positives.
  • A caught secret in a PR or commit blocks the change instead of just producing a warning.
  • Anything found leaked gets rotated, so it stops being usable even though it may still be visible in history.
Tooling / Tech Stack
  • gitleaks, run locally via a pre-commit hook, in CI on every PR, and once against the full git history
  • GitHub's repository security settings, evaluated as an optional second layer
Definition of Ready
  • The scanning rules and allow-list are agreed on before any of the individual checks (local, PR, history) are wired up.
Definition of Done
  • Secrets are caught automatically both locally and in CI, and a finding blocks the change.
  • The one-off history scan and the GitHub-scanning decision are completed and documented rather than left open.
  • Anything found leaked has been rotated.
