What it checks

The 5 functionalities from Part 1 of this report, driven through a real browser against the real app: sign up, log in, add an API key, chat, attach a file, log out.

Tooling
  • Playwright
  • Docker-based mock backend
Cadence

Every pull request.

Testing strategy

One Playwright config, e2e/playwright.config.ts, one chromium project, run against the real app in Docker (shell on port 8000) with the mock LLM standing in for the provider. The five flows live in their own spec files: login, registration, logout, api-keys and chat-management (the last one also covers attach-file). Each test gets a 60 s timeout and assertions a 10 s expect timeout. The suite runs serially (fullyParallel: false) because two of the flows need several concurrent browser contexts of their own against a single shared Ollama instance, so CI caps it at 2 workers and retries a failure once; locally it runs unparalleled with no retries. A failure keeps its trace, a screenshot and a video; every run writes a JUnit XML file for the pipeline.

The GitHub Actions job (.github/workflows/e2e.yml) caps the whole run at 30 minutes and brings the compose stack up with AUTH_RATE_LIMIT_MAX=0, since the suite's logins alone exceed auth-service's default 300 requests per 15 minutes. A failing test fails the job.

Full epic details, from Jira

Description

End-to-end tests for the core things a user does in the app: signing up, logging in, setting up a provider API key, chatting (including attaching files), and logging out. These run against the real app with a browser, using a mock backend in place of the actual LLM provider so the tests don't depend on a live API key or cost anything to run.

Inputs
  • Email and password (registration and login)
  • Provider API key value
  • Chat message text
  • File attachment (type and size)
  • An active logged-in session (for logout)
Acceptance Criteria
  • A new user can register with a valid email and password and lands in the app logged in.
  • A registered user can log in with correct credentials and gets rejected with a clear error on wrong ones.
  • A user can save a provider API key and the app accepts it in a valid format and rejects an invalid one.
  • A user can send a chat message and see it appear; a message right at the 30,000-character limit is accepted, and anything over it is rejected with a clear error instead of being sent.
  • A user can attach a file within the allowed size/type and gets a clear error if it's too big or the wrong type.
  • A user can log out and is sent back to the login screen with the session cleared.
Tooling / Tech Stack
  • Playwright, running against the real app (shell + micro-frontends) in a browser
  • Docker-based mock backend standing in for the LLM provider, so no real API key or cost is needed
  • Runs in CI on every pull request
Definition of Ready
  • The limits and rules above (password rules, API key format, message length, file size/type) are agreed and documented.
  • The mock backend is available so tests don't need a real provider key.
Definition of Done
  • All the acceptance criteria above pass in an automated test run.
  • A failure here blocks the merge.
  • Anything not yet automated (right now: the exact 30,000-character boundary) is called out instead of silently skipped.
