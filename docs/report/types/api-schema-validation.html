What it checks

Requests and responses on every route checked against the shared Zod schemas, including the 32,000-character chat message limit and the SSE event shapes.

Tooling
  • Zod
  • Schemathesis against the generated OpenAPI spec
Cadence

Every pull request.

Testing strategy

Three layers, in order. Inside the process, supertest hits every route of both services and strict-parses the body with the same Zod schema the route itself uses, so a response has to match exactly what the spec says (additionalProperties: false on every object, request and response). A negative-request table then sends the inputs nobody wrote a happy-path test for: 40 rows against conversation-service, 16 against auth-service, covering a missing field, a wrong type, a value outside what's allowed, a field that's too long, an extra field, malformed JSON, a body over 100 kB, a path parameter that can't be decoded, and a bad upload MIME type or size. Every one of those has to come back 400 with a fieldErrors body, never a 500.

Schemathesis runs against the real auth-service and conversation-service containers (pnpm mock:up, mock LLM), signed in as a seeded user, about 1,200 requests across both specs in total. Three operations are excluded on purpose: deleting the signed-in account mid-run, the internal erasure endpoint (service-token only, covered elsewhere), and the SSE stream, which never ends. Because that volume would otherwise trip auth-service's own rate limiter, the CI workflow raises RATE_LIMIT_MAX from its default of 300 to 100,000 for the run. The job is named api-schema / schemathesis and runs on every pull request; the first real run it caught a malformed multipart upload answering 500 instead of 400, fixed in the attachment route's error handling.

Full epic details, from Jira

Description

This epic covers making sure the data moving between the backend and the frontend actually matches what's documented. Auth-service and conversation-service validate every request and response against shared schemas, those schemas get turned into a proper OpenAPI contract, and that contract gets fuzz-tested automatically. It matters because the shell and every micro-frontend - chat, auth, settings - depend entirely on backend responses having a shape they can trust, and silent drift here causes broken UI or leaked data instead of a clear error.

Inputs
  • The request and response shapes defined by each service's existing Zod schemas
  • The routes exposed by auth-service and conversation-service
  • The server-sent events streamed during a chat reply
Acceptance Criteria
  • Every route has a single, documented schema governing its requests and responses, with no undocumented gaps.
  • An invalid request is always rejected with a clear, field-level error instead of a generic failure or a crash.
  • A response that doesn't match its own schema never reaches the client - it's caught and logged as a server-side bug.
  • Streamed chat events are validated as they arrive, so a malformed chunk is logged and handled rather than breaking the chat view.
  • Automated fuzzing against the generated contract catches edge cases nobody thought to write a test for.
Tooling / Tech Stack
  • Zod for schema definitions and validation in both services
  • An OpenAPI generator built on those schemas
  • Schemathesis for property-based contract fuzzing
  • Vitest, running in CI on every pull request
Definition of Ready
  • The services' existing Zod schemas are stable enough to serve as the source of truth.
Definition of Done
  • Every story under this epic passes its own acceptance criteria automatically in CI.
  • A schema or contract violation anywhere in this area blocks the merge.
