Penetration testing

View on Jira, AICHAT-29 ↗ How to run → Evidence →
Security Non-functional Black-box
What it checks

A manual, time-boxed attempt to break into the deployed app: authentication and authorisation, file uploads, public endpoints, browser security, and the risks specific to an LLM-backed product.

Tooling
  • Manual testing
  • Burp Suite / ZAP as aids
Cadence

Per milestone, scoped and time-boxed in advance.

Testing strategy

One harness, testing/pentest/run.ts, drives a local staging copy of auth-service and conversation-service over 127.0.0.1 and turns a code-review finding into a live probe. It is grey-box: the testers read the source first, then try to confirm or refute each hypothesis against the running app, scoring anything confirmed with CVSS v3.1.

#HypothesisWhat it doesIf confirmed
H1Chat sharing by unverified emailInvites an unregistered address to a chat, then registers that address and reads the chatHigh, CVSS 7.1
H2Forgeable JWTSigns an HS256 token with the documented insecure default secret and calls GET /chats with it as a Bearer tokenCritical, CVSS 9.8
H3Refresh-token family not revokedSteals a cookie, refreshes once, then replays the original; checks whether the rotated child token still works after the reuse is rejectedMedium, CVSS 5.3
H4Shared rate-limit bucketSends 4 login attempts, each with a different spoofed X-Forwarded-For, and watches whether RateLimit-Remaining still fallsMedium, CVSS 5.3
H5IDOR on chat readsAn outsider with no membership tries to read a chat by id directlyHigh, CVSS 6.5
H7Public metrics endpointsRequests /metrics on both services with no credentials and checks for Prometheus outputLow, CVSS 5.3

Each run reports confirmed, refuted or inconclusive per hypothesis, never a pass/fail count: a refuted hypothesis here is the secure outcome, not a failure to find one. The harness only ever talks to the staging copy named in its environment, never production or a model provider, and the rate-limit probe sends exactly 4 requests, never a flood, per the written rules of engagement.

The written scope (docs/AICHAT-29/RULES-OF-ENGAGEMENT.md) covers 11 hypotheses in total (H1 to H11) against the shell app, the three remote apps, and the /auth/*, /api/*, /grafana and /collect routes, in one time-boxed session with the report written the same day. The automated harness above implements the six that reduce to a repeatable HTTP check (H1 to H5, H7); the rest (uploads, browser headers, LLM-specific risks, remotes, secrets) stay manual, checked by hand against the same staging copy.

Full epic details, from Jira

Description

This covers a manual, time-boxed penetration test of the deployed chat platform, login and signup, chat, settings, and the backend services behind them. Rather than relying only on automated scanning, a person actively tries to break authentication, authorisation, file handling, and the LLM-specific parts of the app, following a written, agreed scope so nothing happens that wasn't signed off. It matters because some risks, like one user reaching another's data or a crafted prompt leaking something it shouldn't, are easiest to catch by someone deliberately trying to cause them.

Inputs
  • A written, signed-off scope and time window for the test
  • A staging environment that mirrors production closely enough to test safely
  • Test accounts, tokens, and sample files for probing the app's defences
Acceptance Criteria
  • Testing only happens within an agreed scope and time window, against an environment that won't put production at risk.
  • Authentication and authorisation hold up under direct probing, unverified accounts, token handling, rate limits, and cross-user access are all checked.
  • File uploads, publicly reachable endpoints, browser-level protections and LLM-specific risks are checked the same way.
  • Every confirmed issue is scored for severity and written up with enough detail to reproduce and fix it.
  • Anything High or Critical gets fixed and retested, or deliberately deferred with a documented reason, before the test is considered closed.
Tooling / Tech Stack
  • Burp Suite / OWASP ZAP for intercepting and crafting requests
  • jwt_tool for token inspection and tampering
  • ffuf for endpoint discovery
  • CVSS v3.1 for scoring findings
Definition of Ready
  • The rules of engagement are agreed and signed off, and a staging environment is ready to test against.
Definition of Done
  • All High/Critical findings are fixed and retested or explicitly deferred, and the final report is complete and reviewed.
