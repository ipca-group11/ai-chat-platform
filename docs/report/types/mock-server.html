What it checks

A stateful stand-in for both backend services and the LLM providers, so every other test in this project can run without a real database or a paid API key.

Tooling
  • Express
  • Server-sent events for streaming replies
  • Docker Compose profile
Cadence

Built once, used by almost every other test type.

Testing strategy

The server itself has no load profile to tune, it's an Express app other tests point at instead of the real services. Its own correctness is checked with a Vitest suite under testing/mock-server/src: unit specs per router (auth, conversation, anthropic, openai, remotes, collect) plus a contract layer in src/contract that checks every mock response twice, once against the real services' own schemas and once against @platform/shared-types, so a drift between the two fails the build instead of surfacing later in a consuming test. The last recorded run covers 1095 lines (99.26%) and 549 branches (93.07%).

On top of the random error rate, POST /__admin/faults lets a test pin one of 4 named scenarios (session-expired, error-500, slow, stream-drop) to a specific route, for a fixed number of requests or every time. slow holds the response for 3000 ms by default, and stream-drop cuts an SSE stream after 3 events, which is how the SSE reconnection and remote failure epics get a deterministic failure to test against instead of waiting on a real outage.

Full epic details, from Jira

Description

This epic covers the mock server that stands in for everything external the AI chat platform talks to: the Anthropic and OpenAI LLM APIs, the platform's own auth and conversation services, the micro-frontend remotes, and the telemetry collector. It matters because it's the foundation almost every other testing effort on this project builds on, without it, those tests would need real API keys, a live database, and the full stack running just to get started.

Inputs
  • Requests shaped like the real Anthropic, OpenAI, auth-service and conversation-service APIs
  • Configuration selecting which mock behaviour or failure scenario to simulate
  • Named seed datasets to start from
Acceptance Criteria
  • Every one of those external dependencies has a working mock that other tests can run against instead of the real thing.
  • Each mock can be told, per request, to behave normally, slowly, or to fail in a specific realistic way.
  • The mocks' responses stay faithful to the real APIs' schemas, checked automatically rather than assumed.
  • The whole stack can be started against the mocks with one command, loaded with realistic, reproducible data.
Tooling / Tech Stack
  • Express for the mock server and its admin endpoints
  • Docker and Docker Compose for running it standalone or alongside the frontend
  • Playwright for exercising the real app against it end to end
Definition of Ready
  • The scope of what needs mocking (LLM providers, backend services, MFE remotes, telemetry) is agreed.
Definition of Done
  • Every piece above works and is checked automatically in CI.
  • Other testing work across the project can run against this mock server without needing real credentials or infrastructure.
