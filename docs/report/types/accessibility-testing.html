Accessibility testing

Non-functional Non-functional Black-box
What it checks

Every page is checked against WCAG, in both light and dark theme. Keyboard navigation and live regions are included, not just colour contrast.

Tooling
  • @axe-core/playwright
  • vitest-axe for component-level checks
Cadence

Every pull request; zero serious/critical violations allowed.

Full epic details, from Jira

Description

This epic covers accessibility testing of the AI chat platform's web UI, making sure the product actually works for people using a screen reader or navigating by keyboard alone, not just that it looks fine visually. It spans everything from deciding what to test, to scanning for violations against a recognized standard, to fixing what's found and exploring cheaper ways to catch problems earlier.

Inputs
  • The set of pages, states and themes the app presents
  • The rendered UI itself, in light and dark theme
  • Keyboard and screen-reader interaction with that UI
Acceptance Criteria
  • Every page of the app is scanned for accessibility violations in both light and dark theme, against the WCAG 2.1 AA standard.
  • Any serious or critical violation found is either fixed or has a documented, owner-approved reason it's being left alone, and blocks the merge until resolved.
  • The app can be fully operated via keyboard, with visible focus and announced live updates for streaming content.
  • There's a clear, documented decision on whether component-level accessibility checks are worth adding alongside the full-page scans.
Tooling / Tech Stack
  • axe-core, via @axe-core/playwright for full-page scans
  • Playwright for keyboard-only interaction checks
  • vitest-axe, evaluated for component-level checks
Definition of Ready
  • The pages, states and themes that need auditing are agreed before scanning starts.
Definition of Done
  • The scan runs automatically in CI and blocks merges on serious/critical violations.
  • Known violations are either fixed or explicitly tracked, not silently ignored.
