Non-Functional Tests/Load testing

Load testing

View on Jira, AICHAT-24 ↗ How to run → Evidence →
Non-functional Non-functional Black-box
What it checks

How many concurrent users and streams the backend can actually hold before it falls over, run against a mock LLM so it costs nothing.

Tooling
  • k6
Cadence

Manual run, used to document the saturation point of the 4 GB VM.

Testing strategy

One script, testing/k6/load.ts, with six scenarios picked by a SCENARIO environment variable. Each one follows the real flow through the shell: register, sign in, create a chat, send a message, read the stream until done.

ScenarioExecutorLoadDurationWhat it finds
smokeper-vu-iterations5 virtual users, 1 iteration eachunder 1 minThe flow still works end to end

soakconstant-arrival-rate20 new streams per second, steady30 min by default (recorded at 5 min)Leaks and drift under sustained load

Thresholds mark saturation, they do not stop the run: REST p95 under 1000 ms, REST failures under 1%, time to first token p95 under 1500 ms, streams ending in done above 99%. Every ramp step carries its own copy of these thresholds, tagged by level, so the summary shows the first step that actually breaks rather than an average across the whole run.

Real numbers from the last recorded run (2026-10-03, see the AICHAT-24 results doc): browsing users hold up to about 400 concurrent, REST p95 143 to 711 ms, failing at 475 (1.02 s). Streams hold to about 160 concurrent at 30 new per second, time to first token p95 1.31 s, failing at 40 per second (7.1 s). The bottleneck is CPU on conversation-service, a single Node process capped at 0.60 of a core, pegged at 100% from 40 streams per second, not memory, which peaks at 1.1 to 1.3 GB of the 3.6 GB container budget on the simulated 2-vCPU, 4 GB VM.

Full epic details, from Jira

Description

This epic is about finding out how much real-world traffic the platform can take before it starts to struggle, and documenting that limit clearly instead of discovering it in production. We simulate growing numbers of concurrent users hitting the chat flow for real - logging in, starting a conversation, sending a message, and streaming the reply - and watch how response times, errors, and the server's own resource usage behave as the load climbs. It runs against a mock AI provider so repeated runs are free and don't depend on any real provider being available.

Inputs
  • A load-testing script that follows the real login-to-reply flow
  • Scenarios that ramp the number of simulated users up and also hold a steady load for longer stretches
  • Resource readings sampled from the running services during those load runs
  • The cloud VM's own constraints - it's a small production-sized machine with 2 processor cores and 4 GB of memory plus 4 GB of swap
Acceptance Criteria
  • The system handles a realistic ramp of concurrent users while keeping message-sending and reply-streaming latency within agreed targets, and errors stay rare.
  • A longer steady load doesn't cause slow degradation - no leaked connections, no creeping memory use.
  • Once response times or error rates start to break down, that point is identified and written up with concrete numbers rather than left as a vague impression.
  • Memory and CPU use on the services are visible throughout a run, so any slowdown can be tied back to actual resource pressure instead of guessed at.
Tooling / Tech Stack
  • k6 for generating and measuring the load
  • A mock AI provider so runs are repeatable and cost nothing
  • Docker's stats interface for sampling container memory and CPU during a run
Definition of Ready
  • The mock AI provider needs to be up and reachable before any of this can run against it.
Definition of Done
  • The load scenarios run successfully against the mock provider and the results are captured.
  • The point where the platform starts to struggle is documented with real numbers, or explicitly flagged as inconclusive if the data doesn't support a firm answer.
  • This isn't yet wired into an automated pipeline - it's run manually against a deployed environment, and that's called out rather than implied otherwise.
