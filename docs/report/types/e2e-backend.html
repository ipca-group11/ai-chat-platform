What it checks

The same user journeys, checked at the backend afterwards. Does the data actually get persisted correctly, not just displayed on screen for a moment?

Tooling
  • Playwright
  • Direct database assertions
Cadence

Every pull request.

Testing strategy

Same Playwright project as the frontend e2e suite (e2e/playwright.config.ts), run through the real browser against the deployed shell, but the specs that belong to this epic (registration.spec.ts, login.spec.ts, logout.spec.ts) add a second check after the UI settles: a direct psql query against the running Postgres container (e2e/src/tests/support/db.ts), reading the auth and conversation schemas directly: password hash stored for the new user, account count by email, message and attachment rows for a chat. A test only passes once the server-side data matches what the screen showed, not just the screen.

Each test gets 60 seconds overall and a 10 second window per assertion (timeout / expect.timeout in the shared config). The suite runs on a single chromium project with fullyParallel: false, since several specs share the same docker-compose Postgres and Ollama instance; CI retries a failing test once and caps the run at 2 workers, both 0 locally.

Full epic details, from Jira

Description

This epic covers end-to-end testing of the backend flows that power the AI chat platform: authentication, conversation management, and sending and streaming messages through a provider adapter. Rather than testing these pieces in isolation, the tests here run against the real services so that regressions in a multi-step server-side flow, like a login that succeeds but issues the wrong token, or a message that sends but never gets persisted, get caught before they reach production.

Inputs
  • Auth credentials and tokens (registration, login, refresh, logout)
  • Conversation data (create, list, rename, delete)
  • Outgoing chat messages and the resulting provider response
  • An existing database state to assert against after each flow
Acceptance Criteria
  • A user can register, log in, refresh their session, and log out, with each step reflected correctly in the issued tokens and session state.
  • A user can create, list, rename and delete a conversation, and can only act on conversations they own.
  • Sending a message triggers a real call to the provider adapter, streams the reply back to the client, and the final message is persisted correctly in the database.
  • Invalid or malformed requests at any of these steps are rejected with a clear error rather than partially applied.
Tooling / Tech Stack
  • Real running instances of the auth service and conversation service, exercised over HTTP and SSE
  • Recorded or stubbed provider responses where calling a live LLM isn't practical
  • Database assertions to confirm the end state of each flow, not just the API response
Definition of Ready
  • The services under test (auth and conversation) are stable enough to run against repeatedly.
Definition of Done
  • The flows described above run automatically and a failure blocks the merge.
  • Anything not yet automated is called out here rather than left silently untested.
