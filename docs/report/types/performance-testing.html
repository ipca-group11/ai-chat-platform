Non-Functional Tests/Performance testing (frontend)

Performance testing (frontend)

View on Jira, AICHAT-21 ↗ How to run → Evidence →
Non-functional Non-functional Black-box
What it checks

How fast each page actually feels to load and respond to input, measured against a budget agreed per page.

Tooling
  • Lighthouse CI
  • Grafana Faro for real-user data
Cadence

Every pull request; a page over its budget fails CI.

Testing strategy

Lighthouse CI audits five pages: /login, /register, /chats, /chats/:id and /settings, 3 runs per page on the desktop preset, median aggregated, defined in lighthouserc.json at the repo root. The run script signs in a seeded user and creates a chat first, so the two pages behind a login get a real session cookie and a real chat id rather than being skipped.

Every assertion is an error-level budget in the assertMatrix, so one page over budget fails the job, not just a warning. A separate mobile config runs the same five pages under simulated throttling (4x CPU slowdown, 150 ms RTT, about 1.6 Mbps throughput, 412px viewport) with looser budgets: LCP under 4000 ms, TBT under 600 ms, CLS under 0.1.

One real run captured against the live /login page scored 81 on performance, with FCP 1.3 s, LCP 2.3 s, TBT 90 ms, CLS 0 and Speed Index 1.9 s, all inside budget (see the evidence page). The lhci assert step in that capture failed on a CLI flag conflict, not a real regression: this repo's config already defines assertMatrix, which can't be combined with a --preset flag on the command line.

Full epic details, from Jira

Description

This epic covers frontend performance testing for the chat platform's pages - the login screen, the chat conversation view, and the settings page. It sets concrete, agreed loading and responsiveness budgets for each page, checks every page automatically against those budgets (including the ones that require being logged in), stops a build from shipping a regression that breaches a budget, and backs those lab measurements with real-user data so the team can see whether the numbers hold up outside a controlled test run.

Inputs
  • The set of pages in the app and their purpose: a public login screen, a page that streams live content, and a settings page
  • Agreed numeric targets for load time, interaction responsiveness, and layout stability per page
  • A deployed environment to measure against, both in a controlled audit and from real visitors
Acceptance Criteria
  • Every page has an explicit, agreed budget for how fast it should load, how quickly it should respond to interaction, and how stable its layout should stay.
  • Every page, including ones that need a login, gets measured automatically and the result is a repeatable, de-noised number rather than a single lucky or unlucky run.
  • A page that breaches its budget stops the build, with a clear explanation of which page and which measurement failed.
  • Real visitor data is collected and shown on a dashboard, so lab results can be checked against what people actually experience.
  • Findings from the first full round of measurement turn into a concrete, prioritised list of fixes rather than being left as numbers nobody acts on.
Tooling / Tech Stack
  • Lighthouse CI for repeatable, automated lab measurements against a staging deployment
  • The web-vitals library feeding Prometheus and Grafana for real-user monitoring in production
  • The existing build pipeline for gating merges on the measured results
Definition of Ready
  • The page inventory and the general shape of acceptable loading and responsiveness are agreed before specific budgets get signed off.
Definition of Done
  • Every page has a signed-off budget, an automated audit, and a build gate enforcing it.
  • Real-user monitoring is live and showing data for every page.
  • The first round of findings has been turned into a prioritised fix list.
