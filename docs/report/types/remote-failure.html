Functional Tests/Remote failure and fallback testing

Remote failure and fallback testing

View on Jira, AICHAT-8 ↗ How to run → Evidence →
Core user flows Functional Black-box
What it checks

One micro-frontend remote is blocked or slowed down on purpose. Does the rest of the app keep working, with a sensible fallback shown for the broken part?

Tooling
  • Playwright route interception
Cadence

Every pull request, as a merge gate.

Full epic details, from Jira

Description

This epic covers how the app behaves when a part of it - sign-in, chat, or settings - fails to load, loads slowly, or breaks partway through a session. Because the app is built from separate pieces that can each fail independently, this testing area makes sure one broken piece shows a clear, scoped message and recovers on its own, instead of taking the whole app down with it.

Inputs
  • Which part of the app is affected (sign-in, chat, or settings)
  • How it fails - blocked outright, slow to respond, or failing partway after it already started loading
  • Whether and how it comes back online afterwards
Acceptance Criteria
  • A broken part of the app shows its own clear message instead of a blank screen or a crash, and the rest of the app keeps working.
  • A slow-loading part shows a loading state first, then swaps smoothly to the real content once it arrives.
  • A part that recovers - whether the user retries or it happens automatically - comes back without needing a full page reload.
  • These checks run automatically on every pull request and a regression blocks the merge.
Tooling / Tech Stack
  • Playwright, driving the real shell app in a browser
  • Network-level request interception to simulate outages and slow responses
Definition of Ready
  • The three areas under test and how to simulate each failure mode are agreed.
Definition of Done
  • All the acceptance criteria above pass automatically in CI.
  • A failure here blocks the merge.
