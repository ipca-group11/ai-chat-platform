Appendix

Jira & Spec-Driven Development

Why every epic on the AICHAT board is written as a full specification before any code or test exists, and how that choice is what makes working with an AI assistant safe instead of risky.

What spec-driven development means here

A normal backlog ticket says what to build in a sentence or two and leaves the rest to whoever picks it up. Spec-driven development flips that order: the detailed, testable description comes first, and it is the thing both a developer and an AI assistant are held to, not a summary of work already decided informally elsewhere.

On this board that means every one of the 30 testing epics follows the same fixed shape: Description, Inputs, Acceptance Criteria, Tooling, Definition of Ready, Definition of Done. Nothing about what "done" means is left to interpretation once an epic is picked up.

Why it matters more with AI in the loop

An AI assistant has no memory of a hallway conversation or an earlier Slack thread. It only has what is written down. A vague ticket gets a plausible-looking but guessed result. A full spec, acceptance criteria included, gives it an unambiguous contract to implement or test against, and gives a human reviewer the same contract to check the result by.

This is also what let automated evidence be collected honestly for this report. Each test type page traces back to the acceptance criteria of its own epic, so a result is either a real pass, a real fail, or an honest note that it could not be run, never a guess dressed up as a result.

Roles and stakeholders

A spec is only as good as who reviews it, and who is allowed to say it's actually done. Architecture and QA are deliberately placed at both ends of the lifecycle: before any build starts, and again before any epic closes. Everyone else sits in between them.

Product Manager

Owns the why. Decides which problem is worth solving and for whom, before it ever becomes a spec.

Product Owner

Owns the spec itself. Writes or approves the Description, Inputs and Acceptance Criteria, and is the one who confirms, at the end, that the result still matches the original intent.

Architects

Stakeholders of the non-functional requirements. Review a spec up front for whether it's buildable and whether it protects the system's security, reliability and performance budgets, then validate at the end that those NFRs actually hold.

Frontend Architect

The stakeholder for the UI/UX side of NFRs specifically, usability, accessibility, UI consistency. Reviews any spec touching the micro-frontends up front, and signs off on it at the end alongside QA.

QA

Validates both functional and non-functional requirements against their acceptance criteria. Reviews a spec up front for whether it's actually testable, then is the final gate: an epic does not close until QA confirms the evidence matches.

Development (with AI assistance)

Builds against the spec once it's ready, with Claude Code carrying out much of the implementation and test-running work described on the previous page.

Architects and QA are the only two rows active at both ends of the table. That's intentional: the same people who judge whether a spec is buildable and testable are the ones who get the final say on whether it was actually met, so the bar doesn't move partway through.

The SDLC, with AI in the loop

What each spec field forces

FieldWhat it forces before work starts
DescriptionA plain statement of what is being tested and why, not a restatement of the title.
InputsThe exact data, environment or tool a test needs, so nothing is assumed to already be set up.
Acceptance CriteriaThe pass/fail condition, written so both a person and an automated check can evaluate it the same way.
ToolingThe specific command or framework to use, so the result is reproducible instead of ad hoc.
Definition of ReadyThe gate before work can start: the spec itself must be complete, not just written.
Definition of DoneThe gate before work can close: evidence exists and matches every acceptance criterion above.

This report is itself the output of that process applied at scale. 30 epics, each written this way, each with its own test type page tracing straight back to its own acceptance criteria and its own evidence.
