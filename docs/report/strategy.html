Testing Strategy

How the 30 testing epics fit together: test levels vs test types, entry and exit criteria, how risk decides priority, what environments and test data each stage needs, and what runs when.

Test levels vs test types

Two different axes, easy to mix up. A level is where in the system a test runs; a type is what quality it checks. Most of this project's 30 epics are a type run at a specific level.

Levels, by scope
  • Unit, one function or hook, isolated
  • Component, one React component, isolated
  • Integration, one service's own routes against fakes
  • Contract, the boundary between two services
  • System / E2E, the whole app through a real browser
Types, by quality checked
  • Functional, does it do the right thing
  • Security, can it be attacked or leak data
  • Performance, is it fast and light enough
  • Reliability, does it survive partial failure
  • Usability, accessibility and visual consistency

The full breakdown, mapped to ISO 25010's quality characteristics, is on the Non-Functional Requirements page.

The test pyramid for this project

E2E (12 suites)
Integration · Contract · API schema
Component · Snapshot
Unit (largest layer, fast, cheap, run on every save)

Most tests sit at the bottom: fast, isolated, no network. Each layer up costs more to run and catches a different class of bug. E2E is the smallest layer on purpose, reserved for full user journeys a lower layer can't see.

Security, performance and accessibility sit outside this pyramid entirely. They check different qualities, not correctness, so they run on their own schedule.

What gets priority

Three things matter most in a multi-user chat app talking to a paid LLM: it can't leak data, the core flow can't break, and the AI's answers have to be shown correctly.

Highest priority
Security

SAST, dependency scanning, secret scanning, container scanning, DAST, pentest, prompt injection, PII masking, GDPR retention.

Highest priority
Core user flows

End-to-end tests, remote failure handling, SSE reconnection, concurrency, stream cancellation, the things a real user hits daily.

High priority
Chat correctness

Provider adapter replay, API schema validation, contract tests, integration tests, making sure the AI's answer is shown right.

How this is decided: risk-based, likelihood × impact. A leaked API key or another user's chat history (security) is both easy to get wrong and expensive if it happens, so it's a merge gate everywhere it can be. A slow Lighthouse score (performance) is real but survivable, so it's a budget check, not a release blocker. The full severity-to-priority mapping used across every epic is on the NFR page.

Test environments

Local

A developer's machine, docker compose up. Unit through E2E all run here.

CI

A fresh GitHub Actions runner per PR, the same Compose stack, torn down after the job.

Staging / production

The Azure VM behind Caddy, only reachable target for DAST, pentest, and the deploy smoke test.

Test data

No real AI provider, ever

The mock server (AICHAT-144) replays recorded Anthropic/OpenAI streams, so tests are deterministic, free, and never depend on a live key.

Isolated, disposable databases

Integration tests use in-memory fake repositories; GDPR/retention tests use Testcontainers, a throwaway Postgres per run, never the shared dev database.

How it's ordered end to end

Each stage only needs the one before it to be usable, not every single test in it finished.

Stage 1 · runs on every PR, nothing to wait for

Mock server, unit tests, SAST, dependency scan, secret scan, container scan, SBOM.

Stage 2 · needs the mock server and units green

Component tests, snapshot tests, contract tests, API schema validation, integration tests.

Stage 3 · needs contracts & integration green

End-to-end (frontend & backend), remote failure, SSE reconnection, concurrency, stream cancellation, provider adapter replay, accessibility, visual regression, bundle size.

Stage 4 · needs a running deploy, not the PR diff

DAST, penetration test, performance, load testing, prompt injection, scheduled, against staging.

Ongoing · every build, not gated on the others

PII masking, GDPR retention, coverage thresholds.
